DataPlug

API monitoring that checks the response, not just the status code.

Live · Development paused

A 200 OK with an empty result is still a failed check. DataPlug calls a saved endpoint on demand or about every five minutes, then checks the HTTP status, one JSON rule and a response-time limit. It fires a webhook when a monitor flips between healthy and down.

The problem.

Small engineering teams often only learn an API has failed when a person notices, or when their monitor treats any HTTP 200 as success. DataPlug is for teams that provide APIs their customers depend on, and teams that depend on critical third-party APIs and need to check them against their own requirements.

What it does.

  • Save up to five monitors: URL, HTTP method, expected status code.
  • Call private endpoints with a bearer token or an API key header.
  • Require one JSON path (e.g. data.status) to exist, or an array to be non-empty.
  • Fail the check if the response is slower than a 1-15 second limit.
  • Run checks manually or on a ~5-minute schedule; view the latest result and recent history (healthy, down, timeout, status code, latency, error).
  • Send a webhook when a monitor changes between healthy and down.

Key product decisions.

  1. Check the response, not only the status code. One JSON path and one check type keep setup to a few fields. Trade-off: a passing check doesn't prove the payload is business-correct.
  2. Active checks, no agent. DataPlug sends its own requests, so there's nothing to install. Trade-off: failures that only real users hit can be missed.
  3. Alert on state change only. Webhooks fire on monitor.failed and monitor.recovered, not on every failed run, so no alert spam. A failed webhook never fails the check.
  4. A narrow free MVP. Five monitors, five-minute checks, a short history, $0, no credit card. Founding-customer pricing was an email conversation, not a checkout. Easy to try; no in-app revenue flow.
  5. Scheduling in the database. A Supabase pg_cron job calls a secured app route about every five minutes, instead of relying on the host's cron.

How it's built.

One Next.js app serves the marketing site, dashboard and the check worker. Supabase handles accounts (Auth) and stores monitors and history (Postgres with row-level security). A database job wakes up every five minutes and calls the deployed app with a shared secret. Local unit tests cover the core decision logic (monitor limits, check timing, latency rounding, auth flows): 72 passing in the documented run.

Status.

Live at dataplug.dev. Completed the Lauunch incubation programme hosted by WNJ Ventures and Hong Kong Science Park. New commercial development is paused; the repository is kept as the record of the MVP.

TraceNote

Voice-first contact capture for event networking, inside Telegram.

Live private beta · Paused

Scan a contact's Telegram QR code and record a short voice note. TraceNote transcribes it, uses AI to extract structured CRM fields and a follow-up draft, and saves a searchable, exportable record. It never sends a message for you.

The problem.

Conferences produce high-intent contacts but weak follow-through. Details live in memory, notes apps or scattered chats; CRM entry is slow; a personal follow-up is easy to put off. TraceNote targets the seconds after a handshake: minimal taps, voice-first, structured output, so follow-up can happen the same day.

Who it's for.

Business development, partnerships and sales people who network at conferences and side events, and solo operators who want a lightweight personal CRM inside Telegram rather than a full CRM setup.

How it works.

  1. Tap "Scan Contact QR" in the bot; a Telegram Mini App reads the contact's profile QR.
  2. Send a voice note about the conversation.
  3. Google Speech-to-Text transcribes it, with phrase hints for names, companies and events.
  4. An LLM returns strict JSON: name, company, role, where you met, context, follow-up action, reminder date and a draft message.
  5. The record is cleaned, saved and confirmed in chat. Search it, list contacts or export to CSV.
  6. If there's a Telegram handle and a draft, review it with Edit, Copy or Open Chat. You send it yourself.

Key product decisions.

  1. Telegram-first, not a standalone app. Users already message contacts there; nothing to install. Trade-off: bound to Telegram's UX and API limits.
  2. Voice note, not a typed form. Fastest capture while walking between booths. Trade-off: transcription and extraction errors, handled with phrase hints and prompt rules (e.g. resolving "next Friday" to a real date).
  3. Structured extraction, not a chatbot. The model must return a fixed JSON schema, which makes records searchable and exportable.
  4. No auto-send. Drafts are suggestions with copy and open-chat shortcuts, preserving trust and user control at the cost of a few extra taps.
  5. Simple infrastructure. SQLite scoped per user and an optional user whitelist for private beta, instead of a managed database and a full auth system.

How it's built.

A Python bot on Railway, a static QR-scanning Mini App on Vercel, Google Cloud Speech-to-Text for transcription, DeepSeek for structured extraction, and SQLite for contacts and lightweight product analytics (an owner-only funnel view).

What I learned.

The pain was weaker than I assumed. Many field BD people capture informally: the strongest make mental notes or write things up in a notebook or back at the hotel, and some already use dedicated capture devices that sync to their CRM. A new capture habit inside Telegram wasn't a strong enough pull, which points to an ICP or pain-intensity mismatch. Next time I'd test how often and how badly the problem hurts before building the full loop.

Status.

The bot and site are live in private beta. Development is paused.
